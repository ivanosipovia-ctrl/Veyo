# Veo Proxy — сайт-генератор видео + внешний API

Клон интерфейса veo-online.ai со своим бэкендом. Ты выбираешь модель, пишешь промпт,
настраиваешь параметры — запрос уходит на upstream, дожидается готовности, видео
**качается к тебе в хранилище** и проигрывается на твоём сайте.

Плюс внешний API под ключ: другие приложения подключаются к `/v1` со своим ключом.

## Запуск локально

```bash
npm install
npm start       # node server.js
```

Открой `http://localhost:3000`. Нужен **Node 24+** (undici@8 требует zstd;
на Node 20 сервер падает с `createZstdDecompress.bind`).

```bash
npm run dev     # node --watch, перезапуск на каждом сохранении
```

Локально ничего настраивать не надо — без `REDIS_HOST` и `DATABASE_URL` всё
пишется в `data/`.

## Деплой на Render

В репозитории уже лежит `render.yaml` — Render подхватит его сам.

1. Залей папку `veo-proxy` на GitHub (**корень репозитория** — иначе Render не найдёт `render.yaml`).
2. На Render: **New → Web Service → Connect репозиторий** (или **New → Blueprint**).
3. Render сам подхватит blueprint и создаст **две** сущности: сервис и бесплатный
   Key Value. Ничего руками вводить не надо.
4. Дождись деплоя, открой **Logs** — увидишь `storage key value (persistent)`.

### Залив на GitHub, если git не установлен (GitHub Desktop)

1. Установи **GitHub Desktop** (https://desktop.github.com), залогинься.
2. **File → Add Local Repository → Add** → укажи папку
   `C:\Users\Asus\OneDrive\Документы\Default Project\veo-proxy`.
   Если папка ещё не репозиторий — кнопка **Create a repository here**:
   Name `veo-proxy`, Local path та же папка, Branch `main`, **не ставь**
   "Git ignore" шаблон (нужен наш `.gitignore`), Initialize with README — выкл.
3. Нажми **Commit to main** (сообщение любое, например `first commit`).
4. **Repository → Push origin**. Если репозитория на GitHub ещё нет —
   GitHub Desktop сам предложит **Create a new repository on GitHub**:
   сделай его **Private**, галочки по умолчанию, Create.
5. Готово: репозиторий залит, `render.yaml` лежит в его корне.

Проверь перед пушем, что в корне репозитория лежит `render.yaml`, а **нет**
папок `node_modules`, `videos`, `data` (их отсекает `.gitignore`).

### Подключение на Render

1. Открой https://dashboard.render.com → **New +** → **Blueprint**.
2. **Connect a repository** → выбери только что созданный `veo-proxy`.
3. Render прочитает `render.yaml` и покажет два ресурса: `kinopoiskai` (web) и
   `veo-store` (Key Value). Жми **Apply**.
4. Дождись деплоя, открой **Logs** сервиса `kinopoiskai` — в строках `storage`
   должно быть `key value`, а не `file`.

Всё. Ключи API создаются вкладкой **API** на сайте и хранятся в `veo-store` —
перезапуск и редеплой сервиса их не трогает.

Что важно в `render.yaml`:

| Поле | Зачем |
|---|---|
| `type: keyvalue`, `name: veo-store` (plan free) | хранилище ключей и истории, создаётся автоматически |
| `REDIS_HOST` / `REDIS_PORT` (fromService) | подставляются в сервис сами |
| `ipAllowList: []` | снаружи недоступен, только из этого воркспейса |
| `maxmemoryPolicy: noeviction` | записи никогда не выкидываются вытеснением |
| `healthCheckPath: /health` | Render пингует его и перезапускает при поломке |
| `autoDeploy: true` | каждый пуш пересобирает сервис |

### Почему на бесплатном плане ничего не стирается

У бесплатного веб-сервиса Render **нет постоянного диска** — файлы уходят при
каждом деплое, рестарте и уходе в сон. Поэтому всё важное лежит не на диске
самого сервиса, а в **отдельном Key Value инстансе**, который создаёт
`render.yaml` автоматически:

| Что | Где хранится | Переживает деплой/сон сервиса |
|---|---|---|
| ключи API | Key Value, ключ `veo:keys` | да |
| история генераций | Key Value, ключ `veo:jobs` | да |
| сами mp4 | локальный кэш + CDN upstream | восстанавливаются сами |
| кэш адресов, user-id | локальный файл | нет, создаётся заново |

**Базы данных тут нет.** Key Value — это хранилище «ключ → значение», без
схемы, миграций и настройки; Render создаёт его тем же yaml, что и сервис.

`store.js` выбирает бэкенд сам, по приоритету:

| Что задано | Хранилище |
|---|---|
| `DATABASE_URL` | Postgres (если вдруг захочешь) |
| `REDIS_HOST` / `REDIS_PORT` | **Render Key Value** — то, что подставляет render.yaml |
| ничего | `data/*.json` — только для локальной разработки |

Про mp4: байты в Key Value не кладутся (бесплатный инстанс — 25 МБ, одного клипа
не хватит). Вместо этого на задании хранится **url его CDN у апстрима**, и если
файла после деплоя уже нет, `/videos/...` качает его заново сам. То есть видео
восстанавливается, а не теряется.

Если хранилище временно недоступно, сервер падает на локальный файл и каждые
10 секунд пытается переподключиться; как только ответит — переносит туда всё,
что накопилось. Импорт идёт через `ON CONFLICT DO NOTHING`, ничего не
перезаписывается.

В интерфейсе состояние видно бейджем вкладки **API**:
зелёный «key value — ничего не пропадает», жёлтый «локальный файл», красный
предупреждение, если на Render почему-то нет хранилища.

Бесплатный сервис засыпает от простоя ~15 минут — первый запрос после простоя
идёт до минуты. Пингуй `/health` внешним монитором, если это мешает.

### Если ключ пропал

Проверить одной командой:

```bash
curl https://твой-домен/health
# "storage":"kv","durable":true     → всё на месте
# "storage":"file","durable":false  → хранилище не подключилось
```

в интерфейсе то же самое — красный бейдж на вкладке **API**.

`file` на Render значит одно из двух: не создался Key Value инстанс либо
`REDIS_HOST` не подставился. Смотри вкладку **Environment** сервиса — там должны
быть `REDIS_HOST` и `REDIS_PORT`. Обычно помогает **Manual Deploy** после того,
как blueprint отработал до конца.

Когда хранилище подключается, сервер сам импортирует в него всё из
`data/api-keys.json` и `history.json` — старые ключи подтягиваются сами, ничего
делать не надо. Локальное зеркало при этом ведётся параллельно и никогда не
затирает ещё не импортированные записи.

Альтернатива — Docker:

```bash
docker build -t veo-proxy .
docker run -p 10000:10000 -v veodata:/data -e DATABASE_URL=postgres://... veo-proxy
```

### После первого деплоя

Незаконченные генерации не теряются: при старте сервер сам находит задания в
статусе `processing` и продолжает их опрашивать (`resuming N unfinished job(s)` в логе).

## API-ключи

Админ-токена нет — эндпоинты ключей открыты, как и панель в интерфейсе.

| Метод | Путь | Тело |
|---|---|---|
| `GET` | `/api/keys` | — |
| `POST` | `/api/keys` | `{name, dailyLimit}` |
| `DELETE` | `/api/keys/:key` | — |

Ключ выдаётся в формате `veo_…` и показывается **один раз** — сохрани сразу.
Хранится в Key Value (`veo:keys`), локально — в `data/api-keys.json`.

Панель в интерфейсе: вкладка **API** → «Создать ключ». Там же список с
использованием за сегодня, кнопки «копировать» и «отозвать», и готовый `curl`
с уже подставленным ключом.

Каждый ключ имеет свой дневной лимит (`dailyLimit`, по умолчанию `KEY_DAILY_LIMIT=100`).
Он считается отдельно от upstream-лимита — это защита твоего сервиса, а не их.

### Внешний API `/v1`

Авторизация: `Authorization: Bearer veo_…` либо `x-api-key: veo_…`.

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/v1/models` | модели, режимы, соотношения |
| `GET` | `/v1/quota` | остаток по ключу + состояние upstream |
| `POST` | `/v1/generate` | создаёт генерацию → `{job_id, status_url}` |
| `GET` | `/v1/jobs` | список заданий этого ключа |
| `GET` | `/v1/jobs/:id` | статус, а когда готово — `video_url` |
| `DELETE` | `/v1/jobs/:id` | удалить задание |
| `POST` | `/v1/upload` | `dataUrl` → url картинки-источника |
| `GET` | `/v1/videos/:file.mp4` | отдать видео, поддерживает `Range` |

Коды: `401` — нет ключа / неизвестен / отозван, `429` — дневной лимит ключа
или лимит upstream, `404` — задание не принадлежит этому ключу.

Задания **изолированы по ключу**: ключ не видит и не может скачать чужие видео.

```bash
# 1. запустить генерацию
curl -X POST https://твой-домен/v1/generate \
  -H "Authorization: Bearer veo_xxx" \
  -H "Content-Type: application/json" \
  -d '{"prompt":"a red fox running through snow","model":"veo3.1-fast","duration":4,"aspect_ratio":"16:9","resolution":"720P"}'

# 2. опрашивать, пока не придёт video_url
curl https://твой-домен/v1/jobs/JOB_ID -H "Authorization: Bearer veo_xxx"

# 3. скачать
curl -o out.mp4 VIDEO_URL -H "Authorization: Bearer veo_xxx"
```

Для браузерных клиентов `CORS_ORIGIN` в `render.yaml` задаёт разрешённый origin
(по умолчанию `*`). Поставь свой домен, если хочешь ограничить.

## Разобранная протокол-секция upstream

| Что | Значение |
|---|---|
| `POST /api/video/job` | создание генерации |
| `POST /api/workflow/query` | статусы по `job_id` |
| `GET /api/workflow/history` | **готовый url видео** — приходит раньше, чем `query` переключается в `succeeded` |
| `POST /api/upload` | загрузка картинки на их OSS, потом `PUT` по выданному адресу |
| Заголовок `user-id` | 32 hex, «отпечаток» посетителя. Хранится в `data/user-id` |
| Заголовок `Request-Create-Id` | `md5(JSON{job_type,estimated_time}) + md5(Request-Time).slice(0,16)` |
| Заголовок `Request-Time` | unix ms |

Тело создания:

```json
{"job_type":"home","estimated_time":220,"model":"veo3.1-fast",
 "prompt":"...","duration":8,"aspect_ratio":"16:9","resolution":"720P"}
```

Ответ: `{"data":{"job_id":"<uuid>"}}`.

| `REDIS_URL` | пусто | полный адрес вместо `REDIS_HOST`+`REDIS_PORT`, если нужно |

| `PROXY_MODE` | `onlimit` | `onlimit` — переключение только при лимите, `always` — всегда через пул, `off` — всегда напрямую |
| `PROXY_URL` | пусто | один свой адрес `http://ip:port` |
| `PROXY_LIST` | пусто | свои адреса через запятую или перенос строки |
| `PROXY_FILE` | `data/proxies.txt` | файл со своими адресами, по одному в строке |
| `PROXY_TARGET` | `200` | сколько адресов держать в пуле |
| `PROXY_BLOCK_MS` | `600000` | как долго напрямую стоит обходить лимитный маршрут |
| `PROXY_BAD_MS` | `300000` | отстойник для отказавшего адреса |
| `PROXY_CONNECT_TIMEOUT_MS` | `8000` | таймаут соединения через адрес |
| `PROXY_VERIFY_BATCH` | `16` | сколько адресов пробовать за проход |
| `PROXY_VERIFY_EVERY_MS` | `15000` | как часто крутить верификатор |
| `PROXY_VERIFIED_TTL_MS` | `600000` | через сколько «доказанный» адрес проверять заново |
| `PROXY_VERIFY_TIMEOUT_MS` | `7000` | таймаут пробы одного адреса |
| `PROXY_PROBE_URL` | `/api/workflow/query` | чем проверять трубу до апстрима |

## Лимиты upstream и смена адреса

Upstream режет **по IP**: код `10304`, «Daily job limit reached». Свежий
`user-id` не помогает — лимит не к отпечатку привязан, а к адресу.

`proxies.js` это обходит. Нормальный ход запроса — напрямую, без оверхеда.
Как только маршрут получает `10304`:

1. он помечается заблокированным на `PROXY_BLOCK_MS`
2. открывается пул адресов (подтягивается из `PROXY_URL` / `PROXY_LIST` /
   `data/proxies.txt` / кэша, а если пусто — из открытого списка)
3. следующая попытка идёт через первый живой адрес из пула
4. отказавший адрес уходит в отстойник на `PROXY_BAD_MS`, берётся следующий
5. параллельно фоном крутится **верификатор**: каждые `PROXY_VERIFY_EVERY_MS`
   он пробует пачкой `PROXY_VERIFY_BATCH` адресов дешёвым запросом и помечает
   рабочие как `proven`. При лимите ротация берёт сначала их — вместо того
   чтобы минутами ходить по мёртвым
6. прошедший адрес **закрепляется за этим заданием** (`item.proxy`): его опрос
   и скачивание идут с того же адреса, иначе задание потеряется при смене

Ошибка «дневной лимит исчерпан» из интерфейса убрана: кнопка не блокируется,
баннер не появляется, `createJob` крутит адреса до восьми попыток и возвращается
либо с заданием, либо с нейтральным «не удалось создать задание».

Два разных отказа апстрима, которые легко перепутать:

| Ответ | Что это | Что делает система |
|---|---|---|
| `10304` / `Create job limit reached` | квота маршрута | смена адреса, повтор |
| `429` / `Too many requests` | троттлинг по частоте | пауза, повтор с тем же адресом |

Свободные списки адресов живут недолго и многие из них мертвы — поэтому пул
фоново обновляется раз в `PROXY_LIST_TTL_MS` и сам отсеивает неответившие.
Для стабильного результата подставь свой список в `PROXY_LIST` или `PROXY_FILE`.

Кратковременный троттлинг (`10301` / HTTP 429) тоже гасится повторами.

Состояние смотреть так:

```bash
curl http://localhost:3000/api/quota
# {"addresses":{"mode":"onlimit","total":200,"alive":125,"proven":5,
#               "directBlocked":false,...},
#  "upstream":{"lastLimitAt":null,"lastCode":null,"rotates":0}}
```

## Структура

```
veo-proxy/
├── server.js           бэкенд: прокси, ключи, опрос, скачивание, статика
├── proxies.js          пул исходящих адресов + ротация на лимите
├── store.js            хранилище: Key Value / Postgres / локальный json
├── public/index.html   весь интерфейс (один файл, без сборки)
├── render.yaml         деплой на Render (сервис + бесплатная база)
├── Dockerfile          альтернативный деплой
├── package.json
├── .env.example
├── videos/             скачанные mp4 (быстрый путь стриминга)
├── data/
│   ├── user-id         «отпечаток» посетителя для upstream
│   ├── api-keys.json   зеркало ключей (страховка и локальный режим)
│   ├── history.json    история, когда нет DATABASE_URL
│   ├── proxies.json    кэш списка адресов
│   └── proxies.txt     свои адреса (необязательно)
├── probe.js            проверка доступности upstream
└── test.js             автономный прогон create → query → скачать
```

На Render в Postgres живут таблицы `api_keys`, `jobs` и `videos` — ключи,
история и сами mp4 переживают любой деплой.

## Что уже проверено

- полный цикл с UI: промпт → задание → опрос → скачивание → плеер, `readyState 4`
- mp4 лежит локально, ссылка не зависит от чужого CDN
- `/v1`: выдача ключа, `Bearer` и `x-api-key`, `401` без ключа, `401` на отозванный,
  изоляция заданий между ключами (`404` на чужое), `429` по лимиту ключа
- `/api/keys` полностью **без авторизации**: создание, список, отзыв
- счётчик лимита ключа: 5 вызовов из 5 прошли, шестой → `429 daily key limit`
- `video_url` уходит через `/v1/videos/`, а не через открытый `/videos/`
- CORS-префлайт `OPTIONS → 204`
- панель ключей: автозагрузка списка, бейдж хранилища, копирование, отзыв
- фолбэк на локальный файл, если `DATABASE_URL` недоступен — сервер стартует
- возобновление незаконченных заданий после рестарта процесса
- пул адресов: подтянулось 200 штук, напрямую `200 via=DIRECT 849ms`
- после `noteLimit` тот же запрос ушёл через пул:
  `200 via=http://103.133.61.239:8080`, ответ апстрима `SUCCESS`
- верификатор отсеивает мёртвые адреса пробой в фоне (`alive 200 → 122`,
  `proven` растёт до 5 — их ротация берёт первыми)
- отказавшие адреса уходят в отстойник (`200 → 196 alive` за один прогон)
- интерфейс без баннера лимита: кнопка активна, фразы «Дневной лимит» в html нет

### Результат решающего теста ротации

Через пять адресов с открытой трубой до апстрима отправлялось реальное
создание задания (это единственный запрос, где вообще есть лимит —
`workflow/query` на него не реагирует):

```
open pipes            5/12 tried
203.85.120.69:8080    LIMITED  http=200  id="Create job limit reached"
8.210.17.35:8443      429      id="HTTP EXCEPTION"  "Too many requests"
103.61.116.138:5678   429      "Too many requests"
69.75.140.157:8080    429      "Too many requests"
103.133.61.239:8080   429      "Too many requests"
```

И второй прогон, когда лимит уже висел на всех маршрутах — девять проходов
через пул дали `rotates: 10`, ни одного созданного задания, на выходе `503`.

Выводы, которые отсюда follows:

- **ротация работает технически**: адрес реально меняется, `Request-Create-Id`
  считается корректно (md5 сверен с их настоящим заголовком), запрос доходит и
  получает HTTP 200
- **лимит оказался не привязан только к IP** — чужой адрес отдал тот же
  `Create job limit reached`, что и прямой маршрут
- **четыре ответа из пяти — не дневная квота, а троттлинг**: пять POST'ов
  подряд в секунду упёрлись в `Too many requests`. В `createJob` между
  попытками стоит пауза именно поэтому, при нормальном темпе генерации он
  накладывается редко

То есть смена работает именно как смена: запрос уходит не напрямую, а через
другой виртуальный адрес, и вместо блокировки «попробуй завтра» система идёт
на следующий адрес, пока один не пройдёт. Отдельный вопрос — пройдёт ли он,
когда квоту режут всем.

Что реально даёт безлимит: **свой пул с живыми адресами** в `PROXY_LIST` или
`PROXY_FILE`. Открытые списки дают в основном датацентр-IP, которые уже
использованы кем-то до тебя, поэтому там много `429` и `limit reached`.
Механика от источника не зависит — вставляешь свой список, и ротация начинает
выдавать по одному живому адресу, пока задание не создастся.
